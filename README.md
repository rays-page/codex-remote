# Codex Remote
A setup for driving OpenAI's Codex from a phone. Built before OpenAI shipped native mobile support, which now covers most of what this was for.

Kept up as a record of the approach.

Where it ended up: `Codex Remote` shipped as a containing iPhone app plus an iMessage extension, with host companions on desktop that made it obvious when you were safe to step away and keep working from your phone.

The handoff plan that drove the iPhone refactor remains in `docs/imessage-extension-handoff.md`.

`Codex Remote` is a self-hosted control surface for Codex:

- a lightweight Windows launcher that stages the official Codex CLI runtime and exposes its websocket `app-server`
- a native macOS host companion that starts, stops, and monitors the same relay contract
- a native iPhone containing app for setup, pairing, defaults, and fallback diagnostics
- an iMessage extension that becomes the primary lightweight control surface inside Messages, with the courier-pod companion persona intact

The design goal is simple: leave a Codex-capable desktop running, step away, and keep steering threads from your phone without remoting into the whole machine.

## What Is In This Repo

- `desktop/`
  - `codex_remote_desktop.py`: launcher, runtime staging, pairing-link generation, background start/stop/status
  - `start_codex_remote.bat`: one-click start entrypoint for a desktop shortcut
  - `stop_codex_remote.bat`: one-click stop entrypoint
  - `install_shortcut.ps1`: creates a `Codex Remote` shortcut on the Windows desktop
  - `tests/`: unit tests for the launcher logic
- `macos/CodexRemoteHost/`
  - SwiftUI host companion for start/stop/restart, pairing QR, logs, and relay health
  - menu bar surface plus main window
  - writes the same pairing and status artifacts the phone app already understands
- `ios/CodexRemote/`
  - SwiftUI containing app for setup and fallback control
  - Messages extension target that reuses the same relay client, models, and control store
- `docs/`
  - setup, security, design direction, and desktop host plans

## How It Works

`Codex Remote` does not pretend to be Codex. It wraps the official local Codex runtime.

1. The desktop host finds the installed Codex app package or runtime binary.
2. It generates a capability token and starts `codex app-server`.
3. It writes `status.json` and `pairing.json` so the host state stays legible.
4. The iPhone app connects over websocket with `Authorization: Bearer <token>`.
5. The app drives the real Codex thread lifecycle: `thread/start`, `thread/list`, `thread/read`, `turn/start`, and `turn/interrupt`.

## Windows Quick Start

From PowerShell in this repo:

```powershell
.\desktop\start_codex_remote.bat
```

Then install the shortcut:

```powershell
powershell -ExecutionPolicy Bypass -File .\desktop\install_shortcut.ps1
```

Useful commands:

```powershell
py -3 .\desktop\codex_remote_desktop.py status
py -3 .\desktop\codex_remote_desktop.py pairing
.\desktop\stop_codex_remote.bat
py -3 .\desktop\codex_remote_desktop.py doctor
py -3 -m unittest discover -s .\desktop\tests -v
```

## macOS Quick Start

From Terminal in this repo:

```bash
cd macos/CodexRemoteHost
./script/build_and_run.sh
```

Useful commands:

```bash
cd macos/CodexRemoteHost
swift test
./script/build_and_run.sh --verify
```

The macOS companion stores relay state in:

```text
~/Library/Application Support/CodexRemote
```

## iPhone App And Messages Extension

Open `ios/CodexRemote/CodexRemote.xcodeproj` on a Mac in Xcode. The app expects:

- websocket URL, for example `ws://192.168.1.50:8765`
- capability token generated by the desktop host
- optional default workspace path
- optional default model and sandbox preference

The containing app accepts a pairing deep link in this format:

```text
codexremote://pair?url=ws%3A%2F%2F192.168.1.50%3A8765&token=YOUR_TOKEN
```

The iPhone app and the Messages extension share state this way:

- App Group for non-secret defaults such as websocket URL, workspace, model, reasoning, and approval preferences
- Keychain Sharing for the capability token

Messages usage is split by presentation style:

- compact mode for connection state, current-thread orientation, and fast actions
- expanded mode for prompt entry, thread resume, model/reasoning changes, approvals, and request-user-input prompts

## Remote Access Outside Your LAN

The desktop host exposes a websocket service. For true away-from-home use, put that websocket behind something you control, for example:

- Tailscale
- Cloudflare Tunnel
- your own reverse proxy with TLS and auth

When you have a public websocket URL, set it in the launcher so the pairing output uses the correct address:

```powershell
python .\desktop\codex_remote_desktop.py launch --public-ws-url wss://your-host.example/ws
```

The macOS host companion exposes the same idea through its advanced settings panel.

## Security Notes

- The host creates a randomly generated capability token.
- The iPhone app sends that token as a bearer token.
- Cleartext `ws://` is enabled in the iOS app because this is a self-hosted tool. Use `wss://` if you expose it beyond your local network.
- The mobile client can start real Codex turns. Treat the token like a password.

More detail is in [docs/security-and-setup.md](docs/security-and-setup.md).
